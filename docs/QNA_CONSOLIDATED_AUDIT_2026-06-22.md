Quant Nanggroe AI is now in a **production-safe monitoring state**, not a fully approved live-money trading state.

The engine is running, syntax is clean across the audited Python code, health checks pass, and the previous false drawdown breach has been corrected. The system is intentionally guarded by `QNA_TRADING_ENABLED=false`, meaning it can monitor and manage existing DB positions but cannot open new positions silently.

The difference is deliberate: live trading requires broker/exchange key validation, order reconciliation, deployment supervision, dependency installation, frontend build verification, and stronger audit controls before it should be allowed to open new positions.

## Critical Findings

### P0 — Live Trading Must Stay Disabled Until Exchange Reconciliation Exists

Current control: `QNA_TRADING_ENABLED=false`.

Do not set this to true until:

- exchange keys are paper or restricted live keys,
- broker positions are reconciled against SQLite positions,
- order ID/fill ID persistence is verified,
- emergency stop has been tested,
- health check is fast and deterministic,
- logs/alerts are confirmed.

### P1 — Frontend Build Is Not Verified

Observed:

```text
sh: next: not found
```

Action:

```bash
npm install
npm run build
cd dashboard && npm install && npm run build
```

Use the root app or `dashboard/` app as canonical; avoid running two divergent dashboards long-term.

### P1 — Worktree Provenance Is Weak

There are many modified/untracked files. This is expected in active development, but production requires a known release snapshot.

Action:

- create release branch,
- review diff,
- commit audited changes,
- tag release,
- deploy from tag.

### P1 — Health Check Is Too Heavy

`health` currently initializes the full engine stack, including strategies and data integrations. It works, but production readiness checks should be fast.

Action:

- split `health` into `health-fast` and `health-deep`,
- fast: DB, env, PID, position count, balance/peak/drawdown,
- deep: provider imports, strategy load, COT/calendar, dashboard.

### P2 — Allocation Model Conflicts With Position Cap

The asset allocation table targets 8 symbols, but `MAX_POSITIONS_TOTAL=3`. Rebalance logs therefore show drift for non-held assets.

Action:

- either increase position cap only after live validation,
- or define a 3-asset production allocation mode,
- or make rebalance aware of safe-mode/cap constraints.

### P2 — Strategy Validation Needs Institutional Reports

Action:

- walk-forward report,
- out-of-sample split,
- per-strategy expectancy,
- market regime attribution,
- slippage/spread sensitivity,
- turnover and capacity estimate,
- max adverse excursion / max favorable excursion.
